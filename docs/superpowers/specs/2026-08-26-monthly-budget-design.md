# مواصفة التصميم: ربط التطبيق بالشهر والمقارنة بين الأشهر

- **التاريخ:** 2026-08-26
- **الفرع:** `feat/monthly-core`
- **الحالة:** معتمدة من المستخدم
- **المراجعة السابقة:** تقرير «دفتر الشهر» — 10 نتائج، أخطرها F1 و F2 و F3

---

## 1. المشكلة

حقل «الشهر» في كل واجهات التطبيق الخمس هو ملصق نصّي فقط. لا يُصفّي البيانات ولا
يُخزّن أكثر من شهر واحد. البحث الشامل في المشروع عن أي منطق تصفية بالتاريخ أو أي
منطق مقارنة أعاد صفرًا في الحالتين.

النتائج التي تعالجها هذه المواصفة:

| المعرّف | الخطورة | النتيجة |
|---|---|---|
| F1 | حرج | الشهر ملصق لا نطاق — التقرير يجمع كل البنود بغضّ النظر عن تاريخها |
| F2 | حرج | لا يوجد أي منطق مقارنة في المشروع |
| F3 | حرج | تبديل الشهر في RN يعيد تسمية نفس البيانات، والحفظ يطمس الشهر السابق |
| F4 | مهم | (جزئيًا) طبقة التخزين — تُعالَج لواجهة الموبايل |
| F9 | تحسين | إخفاء صامت لأخطاء الحفظ |
| F10 | تحسين | العملة مثبّتة بالدولار والواجهة إنجليزية فقط |

نتيجتان إضافيتان اكتُشفتا أثناء التصميم:

| المعرّف | الخطورة | النتيجة |
|---|---|---|
| F11 | مهم | الرسوم البيانية الثلاثة الموجودة في واجهة الموبايل **تعمل لكنها مضلِّلة** — تقرأ من كل البيانات المخلوطة لا من الشهر المعروض |
| F12 | حرج | طبقة الاستمرار فيها أربعة خطافات متنافسة تكتب في مفتاحَي تخزين مختلفين، وسباق حفظ يمكن أن يطمس البيانات بحالة فارغة عند الإقلاع |

## 2. القرارات المعتمدة

هذه قرارات المستخدم، وهي مُلزِمة للتنفيذ:

| القرار | الاختيار |

| ترتيب التنفيذ | المرحلتان 0 و 1 أولًا، ثم البقية |

## 3. حدود النطاق

### داخل النطاق

- `react-native/packages/shared` — النواة المشتركة
- `react-native/apps/mobile` — واجهة الموبايل
- نظافة المستودع وبنية الاختبار

### خارج النطاق

- `budget_manager.py` (CLI) و `budget_manager_gui.py` (Tkinter) و `mobile/` (BeeWare)
  تبقى تعمل كما هي بلا تغيير.
- **لا توحيد بين منطق Python ومنطق TypeScript.** النتيجة F5 (المنطق مكرَّر ثلاث
  مرات) تبقى **مفتوحة جزئيًا**، وهذا مذكور صراحةً لا مُخفى. النواة TypeScript تصبح
  مصدر الحقيقة للتطبيق، وواجهات Python تصبح إرثًا مُجمَّدًا.
- تفكيك `budget_manager_gui.py` (1,074 سطرًا) و `mobile/…/app.py` (637 سطرًا)
  مؤجَّل — النتيجة F7 تبقى مفتوحة لهذين الملفين.

### قيد إلزامي

تطبيق سطح المكتب RN (`apps/desktop`) يستورد `totals` و `expensesByCategory` و
`serialize` و `deserialize` من النواة، و CI يبنيه. لذلك **كل تغيير على النواة
إضافي لا كاسر** — الصادرات الحالية تبقى بتوقيعها وسلوكها الحالي. أي تغيير كاسر
يجب أن يُعالج بتحديث `apps/desktop` في نفس التغيير.

## 4. معمارية النواة المشتركة

الحزمة `@monthly-budget/shared`. وحدات صغيرة، كل وحدة مسؤولية واحدة، وكل وحدة لها
ملف اختبار.

```
packages/shared/src/
  money.ts        parseAmount · formatMoney
  month.ts        MonthKey · monthKey · currentMonthKey · prevKey · nextKey
                  isFutureKey · monthLabel
  categories.ts   التصنيف الجاهز
  model.ts        الأنواع فقط، بلا منطق
  store.ts        emptyStore · getMonth · upsertEntry · removeEntry · monthsWithData
  totals.ts       totalsForMonth · expensesByCategory
  compare.ts      compareMonths
  history.ts      nameSuggestions · amountSuggestions
  recurring.ts    قوالب البنود المتكررة
  migrate.ts      migrateV0toV1
  index.ts        barrel — يُعيد تصدير الواجهة القديمة أيضًا
```

الحدّ المستهدف لكل ملف: 120 سطرًا. الملف الذي يتجاوزه يُقسَم بحسب المسؤولية لا
بحسب العدد.

### 4.1 نموذج البيانات

```ts
type MonthKey = string   // "YYYY-MM" — يُرتَّب معجميًا ترتيبًا زمنيًا صحيحًا

type Income  = { id: string; name: string; category: string; amount: number; date: string }
type Expense = { id: string; name: string; category: string; amount: number; date: string }

type MonthEntry = {
  incomes: Income[]
  expenses: Expense[]
}

type RecurringTemplate = {
  id: string
  kind: 'income' | 'expense'
  name: string
  category: string
  lastAmount: number
  dayOfMonth: number | null
}

type BudgetStore = {
  version: 1
  currency: string          // رمز ISO مثل "SAR" — لا رمز مثبَّت في الكود
  locale: 'ar' | 'en'
  months: Record<MonthKey, MonthEntry>
  recurring: RecurringTemplate[]
}
```

قرارات مقصودة:

- `MonthKey` نصّ لا كائن تاريخ — يُقارَن ويُرتَّب ويُخزَّن كمفتاح JSON بلا تحويل.
- `date` إلزامي على كل بند (لا `optional` كما في النموذج الحالي). البند بلا تاريخ
  مستحيل التصنيف شهريًا، وهو أحد أسباب F1.
- `id` إلزامي — الحذف والتعديل بالفهرس (كما يفعل الكود الحالي) يفسد عند إعادة
  الترتيب أو التصفية.
- `currency` نصّ في المخزن لا ثابت في الكود — علاج F10.

### 4.2 وحدة الشهر

```ts
monthKey(date: string): MonthKey        // "2026-08-14" → "2026-08"
currentMonthKey(): MonthKey             // من تاريخ اليوم
prevKey(k: MonthKey): MonthKey          // "2026-01" → "2025-12"
nextKey(k: MonthKey): MonthKey          // "2026-12" → "2027-01"
isFutureKey(k: MonthKey): boolean
monthLabel(k: MonthKey, locale): string // "أغسطس 2026" | "August 2026"
```

الحالات الحدّية الإلزامية في الاختبارات: عبور نهاية السنة في الاتجاهين، ونصّ غير
صالح، وشهر خارج 1–12.

### 4.3 وحدة المقارنة

```ts
type DeltaStatus = 'new' | 'gone' | 'flat' | 'changed'

type Delta = {
  current: number
  previous: number
  absolute: number           // current − previous
  percent: number | null     // null عندما previous === 0
  status: DeltaStatus
  favorable: boolean | null  // يُحسَب في النواة
}

type MonthComparison = {
  currentKey: MonthKey
  previousKey: MonthKey | null
  income: Delta
  expenses: Delta
  net: Delta
  margin: Delta
  byCategory: Array<{ category: string; delta: Delta }>
}

compareMonths(store: BudgetStore, key: MonthKey): MonthComparison
```

قواعد إلزامية:

1. **`favorable` تُحسَب في النواة لا في الواجهة.** ارتفاع الدخل والصافي والهامش
   مُواتٍ؛ ارتفاع المصروف غير مُواتٍ. هذا يجعل منطق اللون قابلًا للاختبار بدل أن
   يكون مبثوثًا في JSX.
2. **لا قسمة على صفر.** إذا كان `previous === 0` و `current > 0` فالنتيجة
   `percent: null` و `status: 'new'`. وإذا كانا صفرين فـ `status: 'flat'`.
3. **الشهر السابق قد لا يوجد.** حينها `previousKey: null` وتعرض الواجهة حالة
   فارغة صريحة — لا انهيار ولا أصفار مضلِّلة.
4. **الفئات المتناظرة.** `byCategory` يشمل اتحاد فئات الشهرين: الفئة الجديدة
   `status: 'new'`، والمختفية `status: 'gone'`.

### 4.4 التصنيف الجاهز

قائمة ثابتة في `categories.ts`، كل فئة لها `id` ثابت لا يُترجَم، ومفاتيح ترجمة،
وأيقونة.

**فئات المصروف:** الإسكان · الطعام · المواصلات · الفواتير · الصحة · التعليم ·
المشتريات · الترفيه · الاتصالات · الأقساط والديون · الزكاة والصدقات · التوفير ·
أخرى

**فئات الدخل:** الراتب · عمل حر · تجارة · إيجارات · استثمار · هدايا · أخرى

الأيقونات إيموجي وليست خطّ أيقونات. المقايضة مقصودة: الإيموجي بلا تبعية إضافية،
ويُعرَض على المنصّتين، ولا يتأثر باتجاه النص. عيبه أن شكله يتغيّر بين المنصّات —
مقبول مقابل تجنّب تبعية خطّ أيقونات كاملة.

`id` الفئة يُخزَّن في البيانات، والاسم المعروض يأتي من الترجمة. هذا يعني أن تبديل
اللغة لا يفسد البيانات المخزَّنة.

### 4.5 وحدة الاقتراحات

هي ما يجعل «تقليل الكتابة» ممكنًا فعليًا:

```ts
nameSuggestions(store, kind, category): string[]     // أسماء استُخدمت سابقًا
amountSuggestions(store, kind, name): number[]       // مبالغ نفس البند سابقًا
```

المصدر كل الأشهر السابقة، مرتَّبة بالتكرار ثم بالأحدث. بهذا يصبح إدخال «الإيجار
1500» ضغطتين: رقاقة الاسم ثم رقاقة المبلغ.

### 4.6 الترحيل

```ts
migrateV0toV1(raw: unknown): BudgetStore
```

الشكل القديم `{ meta: {year, month}, incomes[], expenses[] }` مخزَّن تحت مفتاح
واحد. قواعد الترحيل:

1. كل بند يُوزَّع على شهره **بحسب `entry.date` الفعلي** — لا بحسب `meta.month`.
   السبب أن F3 جعل `meta` غير موثوق: البنود قد تحمل تواريخ شهر والملصق يقول شهرًا
   آخر. التاريخ على البند هو الأصدق.
2. البند بلا تاريخ صالح يُنسَب إلى `meta.year`/`meta.month` كحلّ أخير.
3. **قبل أي كتابة، يُحفظ الحمل القديم كما هو** تحت مفتاح احتياطي منفصل. لا نطمس
   بيانات مستخدم قائمة تحت أي ظرف.
4. `version` يمنع تكرار الترحيل.
5. الفئات القديمة النصّية الحرّة تُطابَق بالتصنيف الجديد قدر الإمكان، وما لا
   يُطابَق يذهب إلى «أخرى» مع الإبقاء على الاسم الأصلي في `name`.

### 5.1 الاستمرار: البيانات لا تضيع

هذا شرط صريح من المستخدم، ويُعالج F12 و F9. الحالة الحالية معطوبة بأربع طرق:

1. أربعة خطافات `useEffect` متنافسة — اثنان للتحميل واثنان للحفظ.
2. تكتب في **مفتاحَي تخزين مختلفين** (`@MonthlyBudget:current_budget` و
   `budget_data`)، فهناك مصدرا حقيقة والفائز عند الإقلاع غير محدَّد.
3. خطاف الحفظ يعمل على `[budget]` بلا حارس، و `budget` يبدأ فارغًا — فيُطلَق حفظ
   بالحالة الفارغة قبل اكتمال التحميل. سباق يمكن أن يطمس البيانات المخزَّنة.
4. الأخطاء الأربعة كلها تُبلع في `console.error`، وهي غير مرئية في نسخة الإصدار.

#### الضمانات الإلزامية

| # | الضمان |
|---|---|
| P1 | **مفتاح تخزين واحد** ومصدر حقيقة واحد. الخطافات المتنافسة تُحذف كلها. |
| P2 | **حارس التهيئة.** لا تُكتب أي بيانات قبل اكتمال القراءة الأولى. حالة `status: 'loading' \| 'ready' \| 'error'`، والكتابة ممنوعة إلا في `ready`. هذا يقتل سباق الطمس بالحالة الفارغة. |
| P3 | **حفظ تلقائي عند كل تغيير** — إضافة أو تعديل أو حذف. لا زرّ حفظ يدوي، ولا حوار «Quick Save / Share & Save». الحفظ اليدوي يبقى للتصدير إلى ملف فقط، لا للاستمرار. |
| P4 | **كتابة ذرّية.** المخزن يُسلسَل ويُكتب كاملًا في عملية واحدة. لا كتابة جزئية تترك JSON مقطوعًا. |
| P5 | **قراءة متسامحة.** JSON فاسد أو مقطوع لا يُنتج شاشة فارغة صامتة: يُعرض خطأ صريح، وتُحاول القراءة من النسخة الاحتياطية، والحمل الفاسد يُحفظ ولا يُحذف. |
| P6 | **نسخة احتياطية قبل الترحيل.** الحمل القديم يُحفظ خامًا قبل أي كتابة (§4.6). |
| P7 | **أخطاء صريحة.** فشل الكتابة يُرمى ويُعرض للمستخدم كشريط تنبيه. **لا `catch` صامت في مسار بيانات المستخدم** — نمط `except: pass` الموجود في تفضيلات Tkinter لا يُنقَل إلى هنا. |
| P8 | **الاستئناف على آخر حالة.** التطبيق يفتح على شهر اليوم، لكن كل الأشهر المخزَّنة تبقى متاحة للرجوع إليها. |

#### الاختبارات الإلزامية للاستمرار

- كتابة ثم قراءة ثم مطابقة (round-trip) للمخزن كاملًا بعدة أشهر.
- **اختبار انحدار لسباق الطمس:** محاولة حفظ قبل اكتمال التحميل يجب أن تُرفض ولا
  تُغيّر المخزَّن.
- JSON فاسد عند القراءة ⇒ حالة خطأ صريحة، والحمل الأصلي لم يُحذف.
- مفتاح غير موجود (أول تشغيل) ⇒ مخزن فارغ صالح، لا انهيار.
- الترحيل ⇒ النسخة الاحتياطية موجودة، والبيانات موزَّعة على أشهرها.

> **ملاحظة على المدى:** التخزين محلّي على الجهاز. حذف التطبيق يحذف بياناته. لذلك
> يبقى التصدير إلى ملف متاحًا كنسخة احتياطية يملكها المستخدم. المزامنة السحابية
> خارج نطاق هذه المواصفة، وتُذكَر هنا حتى لا يُفهم «لا تضيع البيانات» على أنه
> يشمل فقدان الجهاز.

### 5.2 شاشة الإضافة

ستّ خطوات، الكتابة في واحدة فقط:

| الخطوة | الأسلوب | الكتابة |
|---|---|---|
| النوع | زرّان كبيران: دخل / مصروف | لا |
| الفئة | شبكة رقائق بأيقونات | لا |
| البند | رقائق أسماء سابقة في الفئة + «أخرى» | عند «أخرى» فقط |
| المبلغ | حقل رقمي + رقائق اقتراح | **نعم — بقرار المستخدم** |
| التاريخ | اليوم · أمس · أول الشهر · آخر الشهر · شبكة أيام | لا |
| التكرار | مفتاح: مرة واحدة / شهري | لا |

### 5.3 الرسوم

مكوّنات خاصة فوق `react-native-svg` (مثبَّت أصلًا كتبعية مباشرة وغير مستخدَم).
`react-native-chart-kit` يُحذف.

أسباب الحذف، وكلها تخصّ هذا التطبيق تحديدًا:

- لا يوفّر أعمدة متجاورة، وهي الرسم المطلوب الوحيد.
- لا يدعم RTL، والواجهة ستكون عربية.
- الكود الحالي يقصّ أسماء الفئات بـ `substring(0, 8)`، وهو مدمِّر للعربية.

الرسوم المطلوبة:

1. **أعمدة متجاورة** — الشهر الحالي مقابل السابق لكل فئة. تبويب المقارنة.
2. **الرسوم الموجودة** تُعاد بناءً بمكوّناتنا وتقرأ من الشهر المعروض فقط — علاج F11.

`scale.ts` يفصل حساب المقاييس والمحاور عن الرسم، فيصبح قابلًا للاختبار بلا تصيير.

## 6. الاختبارات

النواة تُختبر بـ jest، وتغطيتها مفروضة في CI كما هي مفروضة على Python (علاج F8).

اختبارات إلزامية:

- `month.ts` — عبور نهاية السنة في الاتجاهين، مدخلات غير صالحة
- `compare.ts` — القسمة على صفر، غياب الشهر السابق، الفئة الجديدة، الفئة
  المختفية، صحّة `favorable` لكل مقياس
- `migrate.ts` — التوزيع بحسب تاريخ البند لا بحسب `meta`، والبند بلا تاريخ،
  ووجود النسخة الاحتياطية، وعدم تكرار الترحيل
- `totals.ts` — أن الحساب مقيَّد بالشهر فعلًا (اختبار انحدار مباشر لـ F1)
- `store.ts` — الإضافة والتعديل والحذف بالمعرّف
- `history.ts` — ترتيب الاقتراحات

اختبار انحدار صريح لـ F3: بناء مخزن فيه شهران، وتبديل الشهر المعروض، والتأكد من
أن بيانات الشهر الآخر لم تُمَس.

## 8. مخاطر معروفة

| الخطر | التخفيف |
|---|---|
| ترحيل يفقد بيانات مستخدم | نسخة احتياطية خام قبل أي كتابة، واختبار ترحيل على الشكل القديم |
| سباق الحفظ يطمس البيانات بحالة فارغة | حارس التهيئة P2، واختبار انحدار صريح يرفض الكتابة قبل اكتمال التحميل |
| حذف التطبيق يحذف البيانات | التصدير إلى ملف يبقى متاحًا كنسخة يملكها المستخدم؛ المزامنة السحابية معلنة خارج النطاق |
| كسر ترجمة `apps/desktop` | تغييرات النواة إضافية فقط؛ CI يبني سطح المكتب ويكشف الكسر |
| RTL يقلب الرسوم | `scale.ts` يحسب بإحداثيات مستقلة عن الاتجاه، والاتجاه يُطبَّق على التصيير فقط |
| F5 تبقى مفتوحة | مُعلَنة صراحةً في هذه المواصفة؛ واجهات Python مُجمَّدة لا محدَّثة |

## 9. ملاحظة على تكلفة CI

المستودع **عام**، فدقائق Actions ومساحة التخزين مجانية فيه. إضافة وظيفة اختبار
للنواة لا تكلّف شيئًا. وإزالة `web/node_modules` مطلوبة لنظافة المستودع وسرعة
استنساخه، لا لتوفير مال. مصفوفة `macos-13` والبناء اليومي المجدول تُركا كما هما
لأن تكلفتهما صفر هنا.
